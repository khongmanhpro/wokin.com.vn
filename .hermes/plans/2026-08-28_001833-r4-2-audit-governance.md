# R4.2 Audit Governance Hardening Implementation Plan

> **For Hermes:** Execute one bounded task at a time with TDD; do not start R5 in this phase.

**Goal:** Make application audit events safe and forensically meaningful behind a reverse proxy without expanding public UI, editorial workflow, deployment, or storage scope.

**Architecture:** Keep `AuditEvents` append-only and server-created. Harden `admin/src/access/audit.ts` so client-controlled forwarded headers are never treated as authoritative by default, and so persisted before/after snapshots have deterministic size limits and explicit truncation markers. Document operational ownership for proxy trust, audit retention, and archival; do not invent a production proxy or compliance policy.

**Tech stack:** Next.js 16, Payload 3.88, TypeScript, PostgreSQL, Node test runner.

## Task 1 — Define trusted request metadata semantics

**Objective:** Ensure audit IP/request metadata cannot claim a spoofed client IP merely because a request supplied `X-Forwarded-For`.

**Files:**
- Modify: `admin/tests/r4-auth-audit.test.ts`
- Modify: `admin/src/access/audit.ts`
- Modify: `docs/payload-environments.md`

**Step 1: Write failing tests**

Add tests proving:

1. A request with only `X-Forwarded-For` and no framework-provided `req.ip` produces no authoritative `ip` field.
2. A framework-provided `req.ip` is persisted.
3. Request ID remains bounded/sanitized and cannot contain secret payload data.

**Step 2: Verify RED**

```bash
cd admin
node --import tsx --test tests/r4-auth-audit.test.ts
```

Expected: failure because current `requestMetadata()` trusts the forwarded header at `admin/src/access/audit.ts`.

**Step 3: Minimal implementation**

Change `requestMetadata()` to use only the trusted framework/server-derived IP value. Do not add an ad-hoc proxy parser unless the runtime has an explicit trusted-proxy contract. Preserve request ID only as correlation metadata, not network identity.

**Step 4: Verify GREEN**

```bash
node --import tsx --test tests/r4-auth-audit.test.ts
npm run typecheck
```

**Step 5: Document operational boundary**

Document that reverse proxy configuration must populate the framework trusted IP path and strip inbound forwarded headers. The app must not treat arbitrary request headers as trusted client identity.

## Task 2 — Bound audit event payloads deterministically

**Objective:** Prevent oversized product/media JSON or long untrusted strings from turning audit logs into a storage/availability risk.

**Files:**
- Modify: `admin/tests/r4-auth-audit.test.ts`
- Modify: `admin/src/access/audit.ts`

**Step 1: Write failing tests**

Cover all of the following:

1. Sensitive keys remain `[REDACTED]` even inside a truncated object.
2. Long strings are truncated at a documented maximum and include a deterministic marker.
3. Excess object keys/array entries are capped and include a marker/count.
4. Normal product audit values remain unchanged.

**Step 2: Verify RED**

```bash
node --import tsx --test tests/r4-auth-audit.test.ts
```

Expected: failure because current sanitizer caps depth/arrays but preserves arbitrary string lengths and object cardinality.

**Step 3: Minimal implementation**

Add named constants in `audit.ts` for maximum depth, array entries, object entries, and string length. Apply limits before persistence. Use explicit serializable markers such as:

```ts
'[TRUNCATED: <original-length> chars]'
'[TRUNCATED: <omitted-count> items]'
```

Do not hash or log omitted raw values in this phase.

**Step 4: Verify GREEN**

```bash
node --import tsx --test tests/r4-auth-audit.test.ts
npm test
npm run typecheck
```

## Task 3 — Define audit retention and privileged-access policy

**Objective:** Close the operational gap without pretending application-level immutability protects against direct PostgreSQL administrators.

**Files:**
- Modify: `docs/payload-environments.md`
- Create: `docs/audit-governance.md`
- Test: `admin/tests/admin-foundation.test.ts` only if documentation/config assertions are already the established pattern

**Content requirements:**

- App-level append-only access is not a defense against privileged DB operations.
- Specify owners for audit review, archive/export, retention duration decision, backup inclusion, and incident retrieval.
- Require separate application and migration/database-admin credentials in staging/production.
- Define no automatic audit deletion until retention and restore requirements are approved.
- State that production rollout requires trusted-proxy validation and audit log backup/restore inclusion.

No invented legal retention duration or compliance claim.

**Acceptance criteria:**

- No production DB, push, deploy, or public architecture change.
